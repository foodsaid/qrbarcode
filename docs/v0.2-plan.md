# v0.2 方案：GS1 Digital Link、Data Matrix、SVG/尺寸、签名二维码、MCP

状态：实施中 · 目标版本 v0.2.0 · 2026-10-25

## 目标

把服务从"通用二维码/条码图片"升级为**面向 SAP B1 中小企业、符合 GS1 规范的 2D 码服务**，赶在 GS1 Sunrise 2027
（零售 POS 2027 年底前能读 2D 码）和欧盟数字产品护照（电池 2027-02-18 起）之前落地。

原则：

- **向后兼容**：现有 `/generate?content=...&type=qrcode|barcode` 的请求和输出保持逐像素不变，Crystal Reports 里已有的公式不用改。
- **供应链不放松**：新依赖同样哈希锁定、14 天冷却、许可证检查；MCP 的依赖不进生产镜像。
- **每个生成结果都能被解码验证**：测试用 zxing-cpp 把生成的图片读回来，核对内容、码制、GS1 标识。

## 依赖选型

| 用途 | 选型 | 许可证 | 理由 |
| :--- | :--- | :--- | :--- |
| Data Matrix、EAN-13、GS1 Data Matrix | zxing-cpp 3.1.1 | Apache-2.0 | 零依赖、有 manylinux wheel；`gs1=True` 实测输出 `]d2` GS1 Data Matrix；自带解码器可用于测试 |
| 二维码 / Code128 的 PNG 与 SVG | 沿用 qrcode、python-barcode | BSD / MIT | 保持现有输出不变；两者都自带 SVG 输出 |
| 签名 | cryptography 50.0.2（Ed25519） | Apache-2.0 / BSD | 事实标准，无已知漏洞 |
| MCP | 官方 `mcp` SDK 2.3.0 | MIT | 19 个依赖，单独锁定为 `requirements-mcp.txt`，不进 Docker 镜像 |

注意：zxing-cpp 会**静默忽略拼错的参数**，所以每个参数都要有测试证明它生效。

## 1. SVG 与尺寸（阶段 1）

`/generate` 新增可选参数，所有码制通用：

| 参数 | 取值 | 默认 | 说明 |
| :--- | :--- | :--- | :--- |
| `format` | `png` / `svg` | `png` | SVG 为矢量，打印任意放大不糊 |
| `scale` | 1–40 | 各码制现有默认 | 每个模块的像素数，打印最可控 |
| `size` | 64–4096 | — | 目标边长（像素），服务端选不超过它的最大 `scale`；与 `scale` 互斥 |
| `border` | 0–10 | 二维码 1，其他按规范 | 静区宽度（模块数） |
| `ec` | `L` `M` `Q` `H` | `L` | 二维码纠错等级；印在易磨损包装上建议 `M` 或 `Q` |
| `text` | `true` / `false` | 一维码 `true` | 一维码下方是否印人可读文字 |

## 2. Data Matrix 与 EAN-13（阶段 1）

- `type=datamatrix`：普通 Data Matrix，适合小件、金属件、医药。
- `type=ean13`：输入 12 位自动补校验位，输入 13 位则校验，错误时返回 400 并给出正确的校验位。
- 由 zxing-cpp 生成；PNG 与 SVG 都支持。

## 3. GS1 Digital Link（阶段 2）

新模块 `gs1.py`，纯函数，无外部依赖：

- 支持的 AI：`01` GTIN（必填）、`10` 批号、`21` 序列号、`11` 生产日期、`13` 包装日期、`15` 最佳食用日期、`17` 有效期。
- 校验：GTIN-8/12/13/14 统一补成 14 位并核对 mod-10 校验位；批号/序列号 ≤20 字符且只能用 GS1 字符集 82；日期为合法 `YYMMDD`（有效期允许 `DD=00` 表示月底）。
- 生成两种载体：
  - **GS1 Digital Link URI**：`https://id.gs1.org/01/09506000134352/10/ABC123?17=271231`，可用 `domain` 换成企业自己的解析域名（必须是 https、不能带查询串）。
  - **GS1 元素串**：`(01)09506000134352(10)ABC123(17)271231`，供 GS1 Data Matrix 使用。
- 接口：
  - `GET /gs1/digital-link?gtin=...&batch=...&expiry=...` → JSON：`uri`、`element_string`、规范化后的各 AI。
  - `GET /generate?type=gs1qr&gtin=...` → GS1 Digital Link 二维码（零售 POS 与手机都能扫）。
  - `GET /generate?type=gs1datamatrix&gtin=...` → GS1 Data Matrix（医药、生鲜追溯常用）。
- 与 SAP B1 字段对应：`OITM.CodeBars` → GTIN，`OBTN.DistNumber` → 批号，`OBTN.ExpDate` → 有效期，可直接在 Crystal Reports 公式里拼 URL。

## 4. 带签名的防伪二维码（阶段 3）

**能解决的**：别人无法伪造一个"我们签发的"新码（例如编造批号、改有效期）。
**不能单独解决的**：原样复印一张真码。这需要每件商品唯一序列号 + 扫描次数记录（需要数据库），列为后续阶段。

设计：

- 密钥：Ed25519 私钥 PEM，通过 `SIGNING_KEY_FILE` 指向 Docker secret（只读挂载），**绝不进仓库或镜像**；`kid` 为公钥 SHA-256 的前 8 字节（base64url）。
- 签发需要鉴权：`POST /sign`，请求头 `Authorization: Bearer <API key>`；服务端只保存 API key 的 SHA-256（`SIGNING_API_KEY_HASHES`），常量时间比较；签发接口单独限流。未配置密钥时 `/sign` 返回 503。
- 签名内容：对规范化后的 URI（去掉 `sig`/`kid` 参数）签名，结果追加为 `&kid=...&sig=<base64url>`。一个 GS1 Digital Link 加签名后仍是合法 URL，普通扫码照常打开。
- 验证：
  - `GET /verify?u=<扫到的完整 URL>` → JSON：`valid`、`kid`、解析出的 GS1 数据；
  - `GET /.well-known/qr-signing-keys.json` 发布公钥（JWKS，OKP/Ed25519），企业自己的解析站点也可以离线验证。
- 密钥轮换：支持多个公钥同时发布（旧 `kid` 继续可验证），只用最新私钥签发。

## 5. MCP 服务器（阶段 4）

- `mcp_server/`，用官方 SDK 的 FastMCP，stdio 传输，可直接配进 Claude Desktop / Claude Code 等客户端。
- 直接调用核心模块（`codes.py`、`gs1.py`），不依赖 Flask，也不需要联网。
- 工具：`generate_code`（全部码制、PNG/SVG）、`build_gs1_digital_link`、`verify_signed_code`。签发不开放给 MCP（私钥只留在服务端）。
- 依赖单独锁定在 `requirements-mcp.txt`，同样哈希校验、冷却期与审计。

## 6. 与 QRprint 的关系

[QRprint](https://github.com/foodsaid/QRprint) 是单文件、纯浏览器、断网可用、"表格不出本机"的批量标签打印工具。
**建议产品打通，代码不合并**：

- 两者的核心承诺相反：QRprint 的卖点是数据不离开浏览器；本服务是服务端 API。合并后要么 QRprint 失去离线与隐私承诺，要么本仓库多出一个与 Python 服务无关的 1 MB 单文件前端。
- 打通的方式：
  1. **共享 GS1 规则**：把 GS1 校验用例做成一份测试向量（JSON），两个项目都跑同一份，保证 QRprint 打出来的 GS1 码与 API 生成的一致；QRprint 增加 GS1 Digital Link 标签模式时直接复用规则。
  2. **互相引用**：README 和 `/docs` 页面互相指向——"批量打印用 QRprint，报表/系统集成用 API"。
  3. **可选托管**：本服务可以在 `/print` 提供 QRprint 页面。由 Flask 发送真正的 `frame-ancestors` 等响应头，正好补上 QRprint 在 GitHub Pages 上无法设置响应头的限制。页面仍然只在浏览器内处理数据。
